# iOS Phase 0 mock File Provider

This spike uses a native SwiftUI app and replicated File Provider extension with an App Group mock catalog. An optional read-only fixture exercises the Rust C ABI asynchronously at `fetchContents`. It has no remote account, credentials, network access, or production sync guarantee. The proposed minimum is iOS 17.0; this is a build baseline, not a validated device support matrix.

## Build and code checks

From the repository root:

```sh
sh core/test-ffi.sh
ios/build-rust.sh host
SUIZAI_RUST_LIB_DIR="$PWD/ios/.rust/host" swift test --package-path ios
ios/build-rust.sh simulator
ios/build-rust.sh device
xcodebuild -project ios/SuizaiPhase0.xcodeproj -target SuizaiPhase0 -sdk iphonesimulator -configuration Debug ARCHS=arm64 ONLY_ACTIVE_ARCH=NO CODE_SIGNING_ALLOWED=NO build
```

Rust 1.85.1 is pinned in `core/rust-toolchain.toml`; use a local `RUSTUP_HOME`/`CARGO_HOME` if the machine has no global Rust. The Swift package exercises the same `MockStore.swift` and `FixtureFetch.swift` compiled into the app and extension. It verifies existing mock behavior, the three fixture languages, asynchronous success, cancellation before dispatch and during the read, completion once, error cleanup, and a native-versus-Rust 100-read host workload. The Xcode target build compiles the app and embedded extension without launching a simulator. `ios/build-rust.sh simulator` and `device` produce separate arm64 static libraries under ignored `ios/.rust/` paths. For a device build, select a development team and register the App Group `group.dev.suizai.phase0` for both bundle IDs; the checked-in bundle IDs are placeholders for this spike.

The CI evidence artifact contains test and Xcode logs plus `SUIZAI_METRIC` build seconds, Rust archive bytes, unsigned app/extension KiB, and host elapsed/peak RSS samples. These are workload-specific observations. A successful unsigned build does not prove actual Files activation or cancellation under OS process termination.

## Opt-in fixture steps / 測試步驟 / テスト手順

The native `Books/Notes/Welcome.txt` and all native item IDs, writes, domain controls, and permissions remain available. The added root-level `SUIZAI-Rust.txt` is read-only and appears only while the App Group setting is enabled. Its content is generated by Rust; File Provider owns dispatch, cancellation, completion, and the temporary URL. The root filename is reserved even when the fixture is disabled: new native files cannot be created or renamed to it. Existing native content is preserved and may be edited or moved. If an older native file already has that name, the app keeps the fixture off and asks for a rename, without changing the native file.

- **台灣正體中文（預設）**：在 SUIZAI App 點「加入 Mock Domain」，開啟「啟用 Rust 測試檔案」，選擇「台灣正體中文」及 0–500 ms 測試延遲。在「檔案」>「瀏覽」>「SUIZAI Mock」> `SUIZAI-Rust.txt` 開啟，確認內容為 `SUIZAI 共用核心測試檔案`。切換語言後重新開啟檔案；確認檔案不能修改，並再次讀取原本的 `Welcome.txt`。即使停用測試，根目錄的 `SUIZAI-Rust.txt` 仍是保留名稱；若已有同名原生檔案，請先自行重新命名再啟用，App 不會改寫該檔案。

Confirm the fixture is read-only and the native `Welcome.txt` still reads normally. The language, delay, and opt-in flag persist in the existing App Group defaults. If Files shows a cached view, reopen the location; for a fresh domain test, remove and add the Mock Domain. Record device model, iOS version, 0/500 ms reads, cancellation by closing the read, and Console errors. Hardware low-memory kills, protected-data lock/unlock, app/extension restart, and real Files lifecycle remain separate device gates.

## Device gate still required

On a signed iOS 17+ physical device, install the app, tap **Add Mock Domain**, and check that **SUIZAI Mock** appears under Files > Browse > Locations. Browse `Books/Notes/Welcome.txt`, open and read it, create and rename a text file and directory, move an item, and delete it. Force quit the main app before browsing again; the extension must still enumerate and materialize from the App Group. Tap **Remove Mock Domain** and verify the location disappears. Test app/extension restart, simultaneous writes, and low-memory extension termination separately. Record the device, OS version, result, and any Console errors. These gates have not been executed by the code build.

## Constraints observed in the design

- The extension reads its own App Group catalog and content, so File Provider requests do not require the main app process. A cross-process file lock serializes catalog writes.
- This is one fixed mock domain; it does not demonstrate multi-account isolation. Removing the domain does not erase App Group mock data, so adding it again restores prior mock changes.
- Domain registration and removal use `NSFileProviderManager`; the system owns extension launch and termination. The main app does not run a background service.
- The mock stores no credentials. A real provider needs Keychain access group credentials, refresh and user-actionable authentication errors. Those are outside this spike.
- File content is copied into a temporary URL for materialization; this mock keeps permanent copies in App Group storage. Real cache protection, backup exclusion, coordinated eviction, write-back recovery, and conflict handling remain future work.
- The fixture is small text files only. The extension labels created files as plain text and reads whole files into memory. Content writes and catalog writes are not one crash-atomic transaction. Base-version conflict handling, idempotent create replay, and recovery after an interrupted write are not implemented.
- Change enumeration uses a persisted sequence and per-container update/deletion journal, including the working set. The log is deliberately unbounded for this tiny local mock; a real provider needs bounded durable anchors, remote event ingestion, and reconciliation.
- File Provider extension execution time, memory, and system scheduling are constrained. No long-running background transfer or retry behavior is claimed here.
